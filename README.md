# site-rag

A RAG chatbot that answers questions using only the content of one public website and
cites the source page of every answer. This repository currently contains the project
skeleton and the persistence layer (`state.db`) of the ingestion pipeline:

```
discover URLs → fetch → extract & clean → enrich & dedupe → chunk → index
```

Each site has its own isolated data directory, `data/<site_id>/`, holding `state.db`.
Later stages will add `raw/`, `clean/`, `index/` and `reports/` next to it.

## Setup

Requires Python 3.11–3.13 (the virtual environment uses 3.12).

```powershell
uv venv --python 3.12 .venv
uv pip install --python .venv\Scripts\python.exe -e ".[dev]"
.venv\Scripts\python.exe -m pytest
```

On a network with TLS inspection, add `--native-tls` to the `uv` commands.

## Layers

```
src/siterag/
├── domain/      pure Python: entities, enums, URL normalization, hashing,
│                failure policy, removal safety guard. No SQLAlchemy.
├── ports/       Protocols for the repositories and the Unit of Work. No SQLAlchemy.
├── adapters/sqlalchemy/
│                ORM models, explicit mappers (ORM ⇄ domain), repositories,
│                Unit of Work, engine (SQLite pragmas), UTCDateTime type, migration runner.
├── config/      pydantic models + YAML loader (fail fast, clear error messages).
├── container.py composition root: reads config and builds concrete objects (manual DI).
└── cli.py       typer CLI.
```

Rules:

- Code outside `adapters/` only sees domain entities and the ports. Replacing the ORM
  means rewriting `adapters/sqlalchemy/` and `container.py`, nothing else.
  `tests/test_architecture.py` enforces that `domain/` and `ports/` never import
  SQLAlchemy, and that every entity field has a matching column.
- Nothing site-specific is in code. Everything about a site lives in `sites/<site_id>.yaml`.
- Every timestamp is a timezone-aware UTC `datetime`. The database stores them as
  fixed-width ISO-8601 strings (`2026-10-11T10:00:00.000000+00:00`), so text order equals
  time order. Naive datetimes are rejected.
- Each SQLite connection sets `journal_mode=WAL`, `foreign_keys=ON` and `busy_timeout=5000`.

### Unit of Work

```python
container = build_container("fnx")
with container.uow() as uow:
    run = uow.runs.start("fnx", "run", {}, container.config_hash,
                         container.site_profile_hash,
                         container.site.run_lock.stale_after_hours)
    page, is_new = uow.pages.upsert_discovered(
        normalize_url(raw, container.url_rules), DiscoveredVia.SITEMAP, None, None, run.run_id)
    uow.commit()
```

You must call `commit()` explicitly. Anything not committed when the block exits,
normally or through an exception, is rolled back.

## Migrations

```powershell
python -m siterag db upgrade --site fnx   # creates data/fnx/ if missing
python -m siterag db status  --site fnx   # pages by status, chunk count, last run
```

To run Alembic by hand, pass the database with `-x db=...`:

```powershell
alembic -x db=data/fnx/state.db upgrade head
alembic -x db=data/fnx/state.db check
alembic -x db=data/fnx/state.db revision --autogenerate -m "describe change"
```

Migrations use `render_as_batch=True` (needed for `ALTER TABLE` on SQLite), and the
models use a naming convention so every constraint has a name. Review autogenerated
revisions before committing them. `tests/test_migrations.py` runs `upgrade head` on an
empty database followed by `alembic check`, so a model change without a migration fails
the tests.

## The receipt mechanism

`pages.status` is for display and reports only. **Work selection uses stage receipts.**

A row in `stage_receipts` (`url_id`, `stage`, `input_hash`, `stage_version`) means:
*"stage X processed input H using logic version V."*

The `settings.yaml` file defines which `pages` column holds each stage's input, and each
stage's current version:

```yaml
pipeline:
  stage_inputs: { extract: raw_hash, chunk: clean_hash, index: chunks_hash }
  versions:     { fetch: "1", extract: "1", chunk: "1", index: "bge-m3:1" }
```

`uow.pages.iter_needing_stage(stage, version)` returns a page when all of these hold:

- the page is active (status not `removed`, `redirected`, `duplicate` or `failed_permanent`);
- its input hash column is not NULL (the previous stage has produced output);
- it has no receipt for the stage, **or** the receipt's `input_hash` differs from the
  current one, **or** the receipt's `stage_version` differs from the current version.

After processing a page, a stage writes its output hash to the page (for example
`clean_hash`) and calls `uow.receipts.upsert(...)`. That output hash is the next stage's
input, so changes flow downstream automatically:

- A changed page gets a new `raw_hash`. Extract runs again and produces a new
  `clean_hash`, which makes chunk run, and so on.
- Bumping a version, for example `chunk: "2"`, selects every active page for that stage
  again on the next run. Because chunk ids are deterministic and `chunks_hash` covers
  ids + texts, `index` re-runs only for pages whose chunks actually changed.

When a page is marked removed, redirected or duplicate, its chunks and `index` receipt
stay in place. `uow.pages.list_pending_unindex()` lists such pages. The unindex step
(a later task) removes them from the index and then deletes the receipt and chunks.

### Failures across runs

`domain/failure_policy.py` contains pure functions. The caller saves the result with
`uow.pages.update(...)` and `uow.events.add(...)`.

- `record_failure` increments `fail_count` at most once per run (using
  `last_failed_run_id`). After `failure.max_consecutive_failed_runs` failed runs the page
  becomes `failed_permanent`.
- `record_success` clears the failure fields.
- A page that was indexed and then fails keeps its chunks and `index` receipt, so the
  last good version stays searchable.
- At the start of a run, call `uow.pages.reset_failures_for_version_change(stage,
  version, run_id)` for each stage. Pages that failed under an older version of that stage
  go back to `failed` (active) with `fail_count = 0`, keeping `last_error` for history.
  A `restored` event is recorded with `details.reason = "stage_version_changed"`.

### Removal safety guard

`domain/safety.py` has two checks. `check_discovery` aborts if discovery found fewer
than `safety.discovery_min_pages` URLs. `check_removals` aborts if removal candidates
(`uow.pages.list_removal_candidates(run_id)`) exceed `safety.removal_max_ratio` of the
active pages (`uow.pages.count_active()`).

## Adding a new stage (no schema change)

1. Add the stage to `config/settings.yaml`:
   ```yaml
   pipeline:
     stage_inputs: { ..., enrich: clean_hash }
     versions:     { ..., enrich: "1" }
   ```
2. In the stage code, select work with `uow.pages.iter_needing_stage("enrich", version)`,
   and after processing call `uow.receipts.upsert(url_id, "enrich", input_hash, version, run_id)`.
3. Put any new per-page metadata in `page.extra` (a JSON column) and save it with
   `uow.pages.update(page)`.

The `stage_receipts` table is keyed by stage name, so it needs no change. A migration is
only needed if the new stage's *input* is a new kind of artifact that requires its own
hash column on `pages`. `stage_inputs` must name an existing `pages` column; this is
checked when the Unit of Work is built.

## Adding a new site (no code or schema change)

1. Create `sites/<site_id>.yaml`. The file name must equal `site_id`.
   ```yaml
   site_id: example
   base_url: https://www.example.com
   url_normalization:
     strip_www: false
     tracking_params: [utm_*, fbclid, gclid]
     keep_params: []            # if non-empty, only these query params are kept
   safety: { removal_max_ratio: 0.15, discovery_min_pages: 50 }
   failure: { max_consecutive_failed_runs: 3 }
   run_lock: { stale_after_hours: 12 }
   ```
2. Run `python -m siterag db upgrade --site example`. This creates `data/example/state.db`.

Each site gets its own database, so sites cannot affect each other.

## URL normalization

`normalize_url(raw, rules)` does the following:

- forces `https`, lowercases the host, drops default ports and the `#fragment`;
- collapses duplicate slashes and removes the trailing slash (except for `/`);
- drops tracking parameters (glob patterns such as `utm_*`), or keeps only `keep_params`
  when set, then sorts parameters by name.

Percent-encoding is decoded and re-applied consistently, so a raw Hebrew URL and its
encoded form give the same result, and nothing is ever double-encoded. The result has:

- `url`: the encoded form, stored in the database;
- `url_display`: the decoded, human-readable form, used in citations;
- `url_id`: `sha1(url)[:16]`.

`www.` is kept unless the profile sets `strip_www: true`.
